# D3D12 on this setup (experimental)

Status 2026-10-31: no D3D12 game tested yet. What works and what does not was
measured with a small probe (`scripts/experimental/dx12probe/`), not with a
real game. Target: Space Engineers 2 (D3D12 only). Space Engineers 1 is D3D11
and goes through DXMT like the other games.

Machine: M4 (10-core GPU), 24 GB, macOS 26.6, Wine Devel 11.18 (Gcenx).
All tests ran in a separate prefix `~/.wine-dx12test`; `~/.wine-steam` and its
saves were not touched.

## Paths

D3D12 needs a D3D12 → Vulkan layer and a Vulkan → Metal driver:

| D3D12 layer | Vulkan driver | Result |
|---|---|---|
| Wine's builtin d3d12 (upstream vkd3d) | MoltenVK (bundled with Wine) | Works up to SM 6.0, FL 11_0, binding tier 1. Too low for current games |
| Wine's builtin d3d12 | KosmicKrisp | Same, binding tier 3 |
| vkd3d-proton 3.1 | MoltenVK | No device: `Robustness2 features not supported`. Dead end |
| vkd3d-proton 3.1 + patch | KosmicKrisp | **Works offscreen up to FL 12_1, SM 6.6** (with overrides). Window present works with DXVK's dxgi (114–120 FPS) |
| D3DMetal (Apple, via CrossOver/GPTK) | — | CrossOver 26.1 lists SE2 as "Installs, Will Not Run" |

KosmicKrisp is LunarG's Mesa Vulkan driver on Metal (Vulkan 1.4 conformant,
macOS 26+). The LunarG SDK only ships it for arm64, but Wine's unix side is
x86_64 (Rosetta), so it was built from Mesa main for x86_64:
`~/dev/kosmickrisp-x86_64/BUILD.md` has the exact steps (commit
`cb0e78684ac5`, arm64 host tools + x86_64 cross build, `-Dplatforms=macos`).

## Probe results

`dx12probe.exe` reports caps, renders a triangle offscreen and reads it back,
runs compute shaders (DXBC, DXIL SM 6.0, DXIL SM 6.6 with wave ops and
uint64) and measures presents/s in a window.

| Test | vkd3d + MoltenVK | vkd3d + KosmicKrisp | vkd3d-proton (patched) + KosmicKrisp |
|---|---|---|---|
| Max feature level | 11_0 | 11_0 | 11_1 (12_1 with override) |
| Max shader model | 6.0 | 6.0 | 6.0 (6.6 with override) |
| Resource binding tier | 1 | 3 | 3 |
| Triangle DXBC / DXIL 6.0 | PASS | PASS | PASS |
| Compute DXBC / DXIL 6.0 | PASS | PASS | PASS |
| Compute SM 6.6 (wave + int64) | FAIL (`Unknown DXIL version 0x106`) | FAIL | PASS |
| Window present (vsync) | 118–120 FPS | 118–120 FPS 114–120 FPS (with DXVK dxgi + patch) |

Overrides used for the last column:
`VKD3D_FEATURE_LEVEL=12_1 VKD3D_SHADER_MODEL=6_6`. Then all offscreen tests
pass, `failures=0`. The window test needs DXVK's dxgi (see below); it passes
with and without the overrides (vsync 114–120 FPS, no vsync 120 FPS, so the
present rate is capped by the display).

## Why the overrides are needed

vkd3d-proton only reports what it can fully back with Vulkan features. On
Metal it is missing:

- **FL 12_0** needs Tiled Resources Tier 2 (sparse binding/residency). KosmicKrisp has no sparse support.
- **FL 12_1** also needs rasterizer-ordered views and conservative rasterization.
- **SM 6.2+** needs denorm control (`shaderDenormPreserveFloat32` etc.). Metal has none.
- **SM 6.6** needs compute derivative groups, int64 buffer atomics, int8 and subgroup size control.

With the overrides vkd3d-proton reports the higher level anyway. A game that
actually uses sparse resources, ROVs or denorm-sensitive math will render
wrong or crash. Most games only check the level and use a subset, so this is
a gamble per game.

## Patch

vkd3d-proton 3.1 refuses to create a device without transform feedback and
without single-texel buffer alignment. Metal has neither.
`patches/vkd3d-proton/0001-allow-metal-vulkan-drivers.patch` turns both
errors into warnings: stream output stays unsupported, unaligned typed buffer
views may misbehave.

Build (v3.1.0, commit `4522cc1a8b13`, mingw cross):

```bash
git clone --recursive https://github.com/HansKristian-Work/vkd3d-proton src
cd src && git checkout v3.1.0 && git submodule update --init --recursive
git apply ../patches/vkd3d-proton/0001-allow-metal-vulkan-drivers.patch
meson setup ../b64 --cross-file build-win64.txt --buildtype release --strip \
    -Denable_tests=false -Denable_extras=false
schwer ninja -C ../b64 -j4
```

The local build lives in `~/dev/vkd3d-proton-build` (`out/` unpatched,
`out-nofxb/` patched).

## dxgi: DXMT vs. D3D12

DXMT replaces `dxgi.dll` in Wine's lib dir. Wine loads builtin DLLs from
there even when a copy sits next to the exe, so D3D12 sees DXMT's dxgi and
`D3D12CreateDevice` fails with `E_NOINTERFACE`.

Workaround used by the probe: copy Wine's original `dxgi.dll.orig`, replace
the `Wine builtin DLL` marker (offset 0x40) with `Xine nativeX DLL`, put it
next to the exe and set `WINEDLLOVERRIDES=dxgi=n`. Wine then loads it as a
native DLL from the exe dir. This works for Wine's d3d12.

vkd3d-proton swapchains need more: they query
`IDXGIVkSwapChainFactory` (`{53cb4ff0-...}`), which only DXVK's dxgi
implements. With Wine's dxgi the query fails and the present loop crashes
with a null pointer.

So the probe can load DXVK's `dxgi.dll` (`DXGI_DLL=...`). It is a real mingw
DLL, so Wine loads it as native from the exe folder with `dxgi=n`. DXVK
v3.1.1 then refuses KosmicKrisp ("No adapters found", missing required
feature `fillModeNonSolid`), because it checks its own D3D11 feature list.
`patches/dxvk/0001-ignore-missing-features-env.patch` adds
`DXVK_IGNORE_MISSING_FEATURES=1`: missing features only log a warning. With
that set, the swapchain works. DXVK's D3D11 path on KosmicKrisp was not
tested and is not expected to work; DXMT stays the D3D11 layer.

Build (v3.1.1, mingw cross, no build problems with GCC 16.2):

```bash
git clone --recursive --branch v3.1.1 https://github.com/doitsujin/dxvk src
cd src && git apply ../patches/dxvk/0001-ignore-missing-features-env.patch
meson setup ../b64 --cross-file build-win64.txt --buildtype release --strip
schwer ninja -C ../b64 -j4 src/dxgi/dxgi.dll
```

Only the `dxgi.dll` target is built (about 200 steps). The local build lives
in `~/dev/dxvk-build` (`out/dxgi.dll`).

## Running the probe

```bash
bash scripts/experimental/dx12probe/run-dx12probe.sh                # Wine vkd3d + MoltenVK
ICD=~/dev/kosmickrisp-x86_64/kosmickrisp_icd.x86_64.json \
D3D12_DIR=~/dev/vkd3d-proton-build/out-nofxb SECONDS_PER_LOOP=0 \
VKD3D_FEATURE_LEVEL=12_1 VKD3D_SHADER_MODEL=6_6 \
WORK_DIR=~/.cache/steam-on-m1-wine/dx12probe-kosmickrisp \
    bash scripts/experimental/dx12probe/run-dx12probe.sh                # vkd3d-proton + KosmicKrisp, offscreen
# window present: add DXGI_DLL=~/dev/dxvk-build/out/dxgi.dll DXVK_IGNORE_MISSING_FEATURES=1 SECONDS_PER_LOOP=4
```

`DXGI_DLL` makes the script copy that file instead of the marker-stripped Wine
dxgi. `DXVK_LOG_PATH=$WORK_DIR` puts DXVK's log next to the probe.

The script builds the probe with mingw, downloads Microsoft's dxc once
(`gh release download`), compiles the DXIL shaders under Wine, and writes
Wine/vkd3d warnings to `$WORK_DIR/probe.err`. Each line of output is
`PASS`/`FAIL`/`INFO` plus the test name; the last line is
`RESULT failures=N`.

## Open points

1. The probe only presents a cleared/triangle frame. A real game may need more of DXVK's swapchain (HDR, tearing, fullscreen) than this tests.
2. Test a real D3D12 game (SE2 is not owned; any small free D3D12 title would do).
3. Performance: SE2 asks for a 4 TFLOP GPU at minimum. The M4 base GPU is about 4.3 TFLOPS before translation overhead; expect "starts, stutters".
4. Package KosmicKrisp and vkd3d-proton as install scripts once a game runs.
